## Why

Stages 1 and 2 now prove real QQ sandbox intake, confidential handler work, exact human approval, and one provider-accepted final group reply, while the bounded DeepSeek-compatible Agent remains isolated in a synthetic evaluation command. The next locked increment is to connect those verified boundaries so one bound handler can explicitly request evidence-grounded model assistance for one QQ API-503 Case without giving the model workflow, approval, or delivery authority.

## What Changes

- Add one dedicated, default-disabled Stage 3 command that requires explicit QQ and live-model confirmation, a current paired sandbox group, an active dual-surface handler binding, an exact combined capability profile, a current reviewed provider/price profile, bounded budgets, and process-only QQ/model credentials.
- Extend the private handler protocol with `WF-ASSIST <case_id> <expected_version>`. Only the bound handler may trigger the single-Agent investigation after privately pulling and accepting the current Case; a customer group message alone never invokes the model.
- Promote the existing closed live Agent loop into that one QQ Case. It receives a normalized redacted issue view plus only the existing tenant-scoped, fixture-local CRM, monitoring, and knowledge observations, and may produce only safe terminal outcomes or a verifier-authorized response candidate.
- Convert a verified model proposal into the current restricted QQ candidate artifact, return its bounded preview and evidence summary only in handler C2C, and preserve `WF-DRAFT` as the human replacement path. A replacement invalidates the model candidate and every linked approval.
- Bind approval to the initiating handler, Case/revision, model invocation, Context Manifest, ordered evidence, candidate, policy/capability versions, workflow version, and expiry. Final group approval and passive QQ delivery continue through the Stage 2 human gate; the model cannot approve or send.
- Add layered offline-fake and real QQ-plus-model acceptance reports with independent verification, usage/cost/latency and failure attribution, deletion evidence, and explicit separation of model candidate verification, human approval, provider acceptance, customer receipt, issue resolution, Case completion, and production readiness.
- Preserve ordinary services, CI, Replay, Stage 1, and Stage 2 as no-live-model paths. Preserve the existing manual-only Stage 2 workflow when the Stage 3 command or capability is absent.

### Non-goals

- No real CRM, monitoring, knowledge, ticketing, or other business-system connector; tool evidence remains checked-in synthetic fixture data behind the existing read-only gateway.
- No automatic model invocation from a customer message, autonomous approval, direct model-to-QQ send, customer receipt/resolution/Case-completion claim, knowledge publication, or production rollout.
- No QQ mail, attachment handling, arbitrary bot commands, active-send fallback, additional groups/tenants/handlers, multi-Agent collaboration, prompt self-modification, 60-task corpus expansion, or claim of production model quality.

## Capabilities

### New Capabilities

- `bounded-live-model-qq-workflow`: Defines Stage 3 activation, the handler-triggered model-assisted QQ Case flow, cross-provider privacy separation, recovery semantics, and layered offline/live acceptance.

### Modified Capabilities

- `bounded-live-model-provider`: Permit the existing provider only in the new explicitly authorized Stage 3 command as well as the isolated evaluation command, with Case/handler-bound invocation evidence and budgets.
- `bounded-investigation-agent-loop`: Allow the closed single-Agent loop to investigate one accepted QQ Case and stop at deterministic verifier-authorized `RESPONSE_READY` or a safe terminal outcome.
- `fixture-investigation-tool-gateway`: Allow the QQ Case context to use only current tenant-scoped synthetic CRM, monitoring, and knowledge observations while retaining zero write or arbitrary-argument authority.
- `response-candidate-verification`: Normalize a verified model draft into the restricted current QQ response artifact, bind it to model/evidence lineage, and keep human replacement and deletion behavior deterministic.
- `qq-handler-approval-and-delivery`: Add the private `WF-ASSIST` command and private model preview while preserving existing handler identity, confidentiality, manual `WF-DRAFT`, group approval, and final-delivery rules.
- `hash-bound-approval-gates`: Bind approval of a model-assisted candidate to its initiating handler, invocation, Context, evidence, policy/capability, Case/revision, workflow version, and expiry.
- `policy-capability-gates`: Add least-privilege model invocation and read-only investigation scopes available only to Stage 3, without weakening the Stage 2 no-model rule or any QQ write gate.
- `versioned-domain-contracts`: Add closed Stage 3 command, integrated model/QQ lineage, safe outcome, and acceptance-report contracts with Python/TypeScript compatibility fixtures.

## Impact

- Affects the cross-platform command surface in `scripts/dev.py`, the Control Worker orchestration, Agent Runtime live-provider boundary, control-kernel QQ handler workflow, read-only fixture tool gateway, policy/verifier/approval bindings, and local append-only evidence stores.
- Reuses the existing QQ WebSocket/passive-reply adapter, dual-surface handler binding, restricted issue/candidate artifacts, OpenAI-compatible provider, deterministic Agent actions, fixture tools, approval parser, and idempotent final delivery; no new general-purpose sender, business connector, or runtime dependency is intended.
- Adds versioned JSON Schemas, Python and TypeScript contracts, fake transports, security/recovery tests, a dedicated Stage 3 runbook, redacted offline/live reports, and independent report verification.
- The only new network authority is bounded public model contact inside the explicit Stage 3 command. Existing Stage 1/2 QQ commands retain their separately scoped real-provider modes, ordinary services and Replay/CI remain offline-first, and every non-Stage 3 command rejects visible Stage 3-only configuration.
